# 实现路径与本地 MVP 范围

总体架构见 [总体方案](./index.md)，完整目标见 [详细设计](./detailed-design.md)。本文件记录实际落地顺序与当前 MVP 的取舍。

当前进度：M0 本地任务闭环已实现；其中时间任务完成本机真实 HTTP 验收，较长任务的恢复与产物下载由自动化测试覆盖。M1 已抽出通用 Worker SDK、加入受控的任务输入/输出 schema、旧 SQLite 数据升级及本地应用声明导入。个人 CLI 已拆为独立 npm 包，支持隔离安装验证，并配置了基于 GitHub Actions OIDC 的发布工作流；npm 名称确认与 Trusted Publisher 配置待发布者完成。PostgreSQL 与 S3 兼容存储尚未实现和联调。

验证用例使用独立时间查询 CLI 和 Worker：CLI 可配置服务器地址并提交时间任务，Worker 以 JSON 返回执行机器的 UTC 时间。自动化测试覆盖进程内 HTTP 路由和三个独立进程的 IPC 测试。2026-10-26，用户在普通本机终端运行 `npm run smoke:time`，回传任务 `bf116fe5-79d5-483c-927b-aa159491fc75` 的成功结果 `2026-10-26T06:01:39.577Z`（UTC），证明本机独立进程的真实 HTTP 链路已打通。跨机器部署和 HTTPS 入口尚未验收。链路说明见 [时间查询闭环](./time-query-flow.md)。

## 路线

| 步骤 | 交付 | 完成条件 |
| --- | --- | --- |
| M0：本地任务闭环 | 单用户登录、CLI 提交/查询、独立 Worker、持久化租约、检查点、进度事件、文件产物 | CLI 能完成一次任务；强制终止 Worker 后能恢复；迟到尝试不能覆盖结果 |
| M1：基础设施替换 | PostgreSQL 队列、S3 兼容对象存储、正式 schema 迁移、JSON Schema 校验、Worker SDK 包 | 保持 `/v1` API 语义，使用 Compose 跑通同一验收用例 |
| M2：管理能力 | 管理台、取消/重试、周期性定时任务、webhook、审计 | 操作都遵守同一状态机，事件与历史可追溯 |
| M3：数据服务 | 声明式资源、受控迁移、CRUD 与权限 | 应用数据隔离，兼容迁移可回滚 |
| M4：多应用发布 | Git 驱动发布、版本切换、健康检查与回滚 | 旧任务仍由匹配旧版本的 Worker 完成 |

## M0 的实现边界

M0 使用 Node.js 内置 HTTP、SQLite 与本地文件目录，因此无需依赖外部服务即可运行和测试。它保留 `/v1` 路径、任务版本、状态、租约和尝试 ID 等核心契约。通用任务接口现已扩展单次计划执行、历史分页、结果读取、Worker 日志和用户侧客户端 SDK，契约见 [任务底座调用与状态契约](./task-platform-flow.md)。M1 将替换存储层；SQLite 的单机事务与本地文件不作为生产部署方案。

M0 包含：

- 一次性初始化所有者账号和示例应用 Worker 凭据；密码用 Node.js `scrypt` 保存哈希，CLI Token 只保存哈希并有期限。
- 内置示例任务 `example-app/report/build`，并支持本地导入其他应用声明；输入按受控 JSON Schema 校验。任务代码随 Worker 部署，不接受上传脚本。
- CLI 登录、应用/任务定义列表、提交、查询、事件追踪、产物下载；任务历史、结果和日志查询。
- 可选 `run_at` 单次计划执行；到点才允许 Worker 领取，截止时间从计划时间计算。
- 应用后端可使用用户侧 `PlatformClient` 调用相同 HTTP API；Worker 侧使用独立 SDK 和凭据。
- 持久化 `queued → running → succeeded/failed` 与租约过期后的 `recovering`；重启时从已确认步骤继续。
- 本地文件产物；只有成功任务关联的产物可下载。
- 幂等提交与旧尝试结果隔离；关键路径的自动化测试。

M0 暂不包含 Web 会话、输入附件、SSE、自动重试、取消、周期性定时计划、webhook、通用数据服务、管理台和多应用发布。这些保持在总体方案对应阶段。首版终端查看进度使用事件游标轮询；M1 可在同一事件模型上加入 SSE。

个人 CLI 的命令结构、配置安全、使用边界和 C1–C3 演进顺序见 [个人 CLI 设计](./personal-cli-design.md)。当前 C1 已落地服务器配置、origin 凭据隔离、三种 JSON 输入、提交等待、历史和结果操作。

## M0 验收

1. 初始化、启动 API 和 Worker 后，CLI 登录并提交示例任务，能看到进度和成功结果，下载文本报告。
2. 执行中终止 Worker；租约到期后启动 Worker，任务进入 `recovering` 并复用已确认的步骤。
3. 两个 Worker 同时领取时只有一个有效尝试；旧尝试在租约过期后不能写入进度或完成任务。
4. 同一幂等键和输入返回原任务；改动输入则返回冲突。
5. 所有状态、事件和产物元数据在 API 重启后仍然存在。

## 与详细设计的差异及升级条件

- M0 的 SQLite `BEGIN IMMEDIATE` 串行化领取；M1 换成 PostgreSQL `FOR UPDATE SKIP LOCKED`，并保留尝试 ID 校验。
- M0 的产物由 API 写入本地文件；M1 换成对象存储签名上传和完成确认。
- M0 使用 `scrypt`；M1 待替换为成熟认证库的 Argon2id。示例任务的输入和输出已改用受控 JSON Schema 子集；后续接入完整校验库。
- M0 自带一个固定示例应用；通用 Worker SDK 与本地应用声明导入已完成。M4 再支持同一应用的多版本发布和回滚。
